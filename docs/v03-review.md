## 问题与复现

### [P2] 统计进入工单中心时刷新列表，避免统计与记录脱节

- **精确位置**：`client/StaffPage.tsx:67-69`（列表加载 effect 仅依赖 load），关联 `client/StaffPage.tsx:193-198`（inspect 只设置筛选并跳转）、`client/StaffAnalytics.tsx:53-74`（统计组件重新进入会独立加载最新数据）。
- **适用条件**：工作人员保持同一页面会话，其他居民或工作人员改变本场地工单后，通过内部导航浏览统计和列表；不依赖非常规输入。
- **复现步骤**：
  1. 工作人员进入工单中心，等待列表加载完成，记下待接单数量 N。
  2. 在另一个居民浏览器会话提交一条手动报修，状态为待接单。
  3. 工作人员点击“数据统计”，统计向服务端重新获取数据，待接单分布显示 N+1。
  4. 点击“待接单”分布进入工单中心。
  5. 工单中心仍使用步骤 1 的 tickets，显示 N 条并缺少刚提交的工单；点击“刷新数据”后才出现。
- **根因证据**：`App` 在这些工作人员路径之间持续渲染同一个 `StaffPage`；`path` 只影响其分支显示，不在列表 effect 的依赖里。统计组件在分支切入时重新挂载，独立请求服务端；`inspect` 不重新请求列表。因此两个界面刷新时机不同。
- **影响**：用户从统计点击“查看某状态的 N+1 条工单”，实际列表显示 N 条，难以找到刚新增或变更的记录；看板也可持续呈现旧状态。
- **建议**：进入工单中心/看板或执行统计跳转时刷新列表，保留筛选状态；在刷新完成前展示加载提示，避免将旧列表标为当前结果。随后增加“两会话新增工单 → 进入统计 → 点击分布 → 列表包含该单”的浏览器回归。
- **验证边界**：已通过本地代码调用链两次独立复核，未在浏览器执行上述复现；已交 root 在其 3031 浏览器验收环境核实。未启动额外服务。
